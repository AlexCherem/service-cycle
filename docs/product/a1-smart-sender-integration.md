# Service Cycle: исследование интеграции A1 Smart-рассылка

Статус: предварительное техническое решение на основе открытых официальных
материалов A1 Беларусь. Перед реализацией адаптера требуется получить закрытую
API-документацию и тестовый доступ от A1.

Дата проверки: 31 августа 2026 года.

## Краткий вывод

A1 Smart-рассылка подходит для нашего сценария сервисных напоминаний. Платформа
официально поддерживает:

- массовые и персональные SMS;
- Viber-сообщения;
- каскад Viber -> SMS при недоставке;
- отложенную отправку и расписание;
- управление скоростью;
- просмотр статусов доставки и статистики;
- загрузку и экспорт XLSX/CSV;
- API-протокол;
- отправку абонентам любых мобильных операторов Беларуси.

Однако открытые страницы A1 не публикуют:

- URL и методы API;
- формат запросов и ответов;
- способ API-аутентификации;
- порядок выпуска API-ключа;
- ограничения скорости и размера пакета;
- список кодов ошибок;
- наличие webhook статусов;
- правила идемпотентности;
- sandbox или тестовый контур.

Поэтому нельзя начинать `A1NotificationSender`, придумывая контракт. Сначала мы
получаем документацию и письменное подтверждение допустимой схемы подключения
стороннего SaaS.

## Что представляет собой Smart-рассылка

Услуга предназначена для бизнеса и доступна юридическим лицам и ИП на
корпоративных тарифах A1, кроме прямо исключённых линеек. Клиент A1 подключает
услугу к своему абонентскому номеру. Этот номер затем используется как логин на
платформе `smart-sender.a1.by`.

Это означает:

- номер телефона является идентификатором корпоративного аккаунта;
- одного произвольного личного номера в настройках Service Cycle недостаточно;
- компания сначала должна подключить услугу у A1;
- списание относится к корпоративной услуге/счёту A1;
- Service Cycle подключается только после активации аккаунта и получения
  разрешённых API-реквизитов.

## Каналы и способы отправки

### SMS

A1 заявляет массовые и персональные SMS. Получателями могут быть абоненты любых
операторов с национальными номерами `+375`, а не только абоненты A1.

Для SMS используется альфа-имя — буквенно-цифровое имя отправителя вместо
телефонного номера. Оно должно:

- соответствовать бренду или фирменному наименованию компании;
- идентифицировать реального отправителя;
- состоять максимум из 11 латинских букв и/или цифр;
- не содержать специальные знаки;
- пройти модерацию A1.

Проверка альфа-имени занимает от 3 до 7 рабочих дней.

### Viber

Viber позволяет отправлять брендированные сообщения с изображением, длинным
текстом и кликабельной кнопкой. Для него регистрируется отдельное альфа-имя.

У Viber-имени есть ежемесячная оплата и особые правила постановки на паузу.
Точные актуальные условия необходимо проверять перед подключением клиента.

### Каскад Viber -> SMS

A1 поддерживает приоритетный канал и автоматическое переключение на запасной.
Практический сценарий:

```text
Попытка Viber
  -> доставлено: завершаем уведомление
  -> не доставлено: отправляем SMS
```

В нашей модели это не одно сообщение с одним статусом, а одно логическое
`Notification` и несколько `NotificationAttempt`.

### Web-интерфейс

Компания может вручную создать рассылку, загрузить XLSX/CSV, выбрать тариф,
поставить отправку в расписание и посмотреть статистику. Этот способ полезен для
первого ручного пилота, но не обеспечивает автоматический продуктовый флоу
Service Cycle.

### API

Официальная продуктовая страница подтверждает рассылку посредством API-протокола.
Официальный публичный контракт API не найден. API должен стать способом
автоматической отправки из Service Cycle только после получения документации от
A1.

## Виды сообщений и влияние на продукт

A1 разделяет SMS на:

- рекламные;
- сервисные/транзакционные;
- информационные.

Напоминание о запланированном событии в рамках предоставления услуг прямо
упоминается среди допустимых информационных/транзакционных сценариев. Это хорошо
соответствует напоминанию о плановом обслуживании.

Для информационных и сервисных сообщений клиент регистрирует шаблоны. Если
структура фактического сообщения отличается от зарегистрированного шаблона, A1
может тарифицировать его как рекламное.

Следствие для Service Cycle: пользователь не должен вводить полностью
произвольный текст непосредственно перед каждой отправкой. Нужны утверждённые
шаблоны и контролируемые переменные.

Пример логического шаблона:

```text
{clientName}, напоминаем: для {equipmentName} рекомендуется обслуживание
{serviceDate}. Выберите действие: {responseUrl}
```

До получения API-документации неизвестно, как A1 обозначает переменные внутри
зарегистрированного шаблона. Этот синтаксис нельзя фиксировать в коде заранее.

## Длина SMS и стоимость сегментов

По правилам A1:

- латинское односегментное SMS — до 160 символов;
- кириллическое односегментное SMS — до 70 символов;
- длинное латинское сообщение разбивается на части по 153 символа;
- длинное кириллическое — на части по 67 символов;
- каждая часть тарифицируется отдельно.

Наш интерфейс шаблона должен показывать:

- фактическую кодировку;
- количество символов;
- предполагаемое число SMS-сегментов;
- предупреждение о росте стоимости;
- длину публичной ссылки.

Так как тексты будут на русском языке, даже короткое напоминание со ссылкой может
занять два или больше сегмента. Нужен короткий домен и компактный непрозрачный
токен публичного ответа.

## Тарифная модель A1

A1 публикует три подхода к тарификации SMS:

- «Базовый» — поштучная тарификация с различием сетей;
- «Единый» — поштучная тарификация во все сети Беларуси;
- «Пакет SMS» — ежемесячная абонентская плата и включённый объём.

На официальной странице на дату исследования опубликованы пакетные варианты с
абонентской платой от 168 BYN в месяц и ценой одного SMS от 0,0336 BYN; более
крупные пакеты снижают цену одного SMS. Тарифы могут меняться, поэтому Service
Cycle не должен хранить их как константы или обещать пользователю точную цену.

Если API не возвращает стоимость и баланс, мы показываем только статистику
сегментов, а финансовые данные пользователь смотрит в кабинете A1.

## Согласия и ответственность

Условия A1 требуют включать в рассылку только получателей, которые дали согласие
на сообщения. Также нельзя продолжать отправку человеку, явно отказавшемуся от
неё.

В Service Cycle необходимы:

```text
notificationsAllowed
consentAt
consentSource
optedOutAt
optOutSource
```

Точную обязательность каждого поля и допустимые способы фиксации согласия нужно
подтвердить с профильным юристом. Технически система обязана уметь немедленно
исключить клиента из будущих отправок.

## Главный вопрос подключения SaaS

Правила A1 запрещают клиенту передавать третьим лицам логин и пароль от системы.
Следовательно, Service Cycle не должен просить пользователя ввести пароль от
кабинета `smart-sender.a1.by`.

Нам требуется один из официально разрешённых вариантов:

1. Отдельный API-ключ, предназначенный для сторонней интеграции.
2. Отдельная техническая учётная запись с ограниченными правами.
3. OAuth или другой flow авторизации без передачи пароля Service Cycle.
4. Партнёрская/реселлерская схема A1 для многопользовательского SaaS.

До письменного ответа A1 поле `password` в нашей модели проектировать нельзя.

Также необходимо выяснить, разрешает ли A1 одному аккаунту Service Cycle
отправлять сообщения от имени нескольких компаний. По текущим правилам
альфа-имя должно соответствовать самому клиенту A1. Поэтому предварительно
безопаснее считать, что каждая компания Service Cycle подключает собственный
аккаунт A1.

## Рекомендуемая модель данных

Названия и поля предварительные. Они описывают нашу предметную область и не
должны повторять неполученный API-контракт A1.

### `NotificationProviderConnection`

Подключение конкретной компании к провайдеру:

```text
id
companyId
provider                A1_SMART_SENDER
status                  DRAFT | PENDING | ACTIVE | ERROR | DISABLED
accountPhoneMasked
smsSenderName
viberSenderName
tariffCode              nullable, только справочная информация
credentialsEncrypted
credentialsVersion
lastCheckedAt
lastError
createdAt
updatedAt
```

Секрет нельзя возвращать через API после сохранения. Для замены секрета нужен
отдельный endpoint, а не обычное редактирование всей настройки.

### `NotificationTemplate`

Шаблон, согласованный с провайдером:

```text
id
companyId
providerConnectionId
channel                 SMS | VIBER
category                SERVICE | INFORMATIONAL | ADVERTISING
name
body
variablesSchema
providerTemplateId      nullable до получения ответа A1
approvalStatus          DRAFT | PENDING | APPROVED | REJECTED
rejectionReason
createdAt
updatedAt
```

### `Notification`

Одно бизнес-напоминание:

```text
id
companyId
clientId
equipmentId
serviceEventId
templateId
recipientPhone
strategy                SMS_ONLY | VIBER_ONLY | VIBER_THEN_SMS
renderedText
responseTokenId
scheduledAt
status
createdAt
updatedAt
```

`Notification` отвечает на вопрос «зачем и кому отправляем», но не хранит только
одну техническую попытку.

### `NotificationAttempt`

Фактическая попытка у провайдера:

```text
id
notificationId
channel
provider
idempotencyKey
providerMessageId
status                  PENDING | ACCEPTED | SENT | DELIVERED | FAILED
segmentCount
estimatedCost
providerErrorCode
providerErrorMessage
requestedAt
acceptedAt
deliveredAt
failedAt
createdAt
updatedAt
```

Для каскада одна `Notification` может иметь попытку Viber и затем попытку SMS.

### `ClientNotificationPreference`

Настройки согласия клиента:

```text
id
companyId
clientId
smsAllowed
viberAllowed
consentAt
consentSource
optedOutAt
optOutSource
updatedAt
```

До консультации с юристом модель считается техническим черновиком.

## Рекомендуемые границы backend-модулей

```text
notifications
  - бизнес-сценарии, шаблоны, статусы и журнал

notification-providers
  - общий интерфейс отправителя
  - A1-адаптер
  - будущие адаптеры МТС/life:)/Telegram

notification-scheduler
  - поиск наступивших напоминаний
  - создание заданий отправки
  - повторы и защита от дублей

public-responses
  - защищённая публичная ссылка
  - ответ клиента и отписка
```

На старте это могут быть части одного NestJS-модуля `notifications`. Выносить
микросервисы не нужно.

## Кто управляет расписанием

A1 умеет отправлять по расписанию, но главным источником времени должен быть
Service Cycle:

1. Service Cycle рассчитывает срок обслуживания.
2. Service Cycle создаёт `Notification`.
3. Наш worker выбирает наступившие уведомления.
4. A1 получает сообщение непосредственно перед требуемой отправкой.

Так отмена или перенос обслуживания не требует синхронизировать большое
количество далёких будущих заданий у провайдера. Возможность расписания A1 можно
использовать позже, если API и надёжность этого потребуют.

## Статусы доставки

A1 показывает статусы онлайн в личном кабинете, но открытая документация не
уточняет способ получения статусов через API. Возможны два варианта:

- A1 вызывает наш webhook;
- Service Cycle периодически запрашивает статус по `providerMessageId`.

Наша модель должна поддерживать оба варианта. Конкретный механизм определяется
только после получения API-документации.

## Полный путь подключения одной компании

### Действия компании у A1

1. Иметь корпоративный договор и подходящий тариф A1.
2. Войти в корпоративный кабинет A1 как Администратор или Супервайзер.
3. Подключить услугу Smart-рассылка к выбранному абонентскому номеру.
4. Зарегистрироваться на `smart-sender.a1.by`, используя этот номер как логин.
5. Выбрать SMS, Viber или оба канала.
6. Подать заявку на нужное альфа-имя.
7. Подтвердить право использовать название компании/бренда.
8. Подать сервисные шаблоны напоминаний.
9. Дождаться модерации альфа-имени, ориентировочно 3–7 рабочих дней.
10. Выбрать тариф.
11. Получить у A1 API-документацию и разрешённые интеграционные реквизиты.
12. Если требуется, сообщить A1 статический IP нашего VPS.
13. Вручную отправить тестовое сообщение через кабинет A1.

### Действия компании в Service Cycle

1. Открыть «Настройки -> Уведомления -> A1».
2. Ознакомиться с чек-листом предварительного подключения A1.
3. Указать маскированный идентификатор аккаунта/номер.
4. Указать утверждённое SMS-альфа-имя.
5. Ввести только выделенный A1 API-ключ или технический токен.
6. Запустить проверку соединения.
7. Сопоставить локальный шаблон с зарегистрированным шаблоном A1.
8. Отправить тестовое SMS на собственный номер.
9. Подтвердить успешное получение.
10. Включить автоматические уведомления и установить дневной лимит.

Если A1 не выдаёт отдельный API-ключ, экран подключения не реализуется до
согласования безопасного механизма.

## Наши пошаговые действия

### Этап 0. Получить ответы A1 до разработки адаптера

1. Обратиться в бизнес-поддержку A1 и сообщить, что Service Cycle —
   многопользовательский SaaS для сервисных компаний.
2. Запросить актуальную API-документацию Smart-рассылки.
3. Запросить тестовый аккаунт или sandbox.
4. Уточнить, разрешено ли хранить API-токен клиента в стороннем SaaS.
5. Уточнить, нужна ли партнёрская схема.
6. Получить письменный ответ по модели «одна компания — один аккаунт A1».
7. Уточнить требования к статическому IP.
8. Получить правила регистрации переменных шаблонов.
9. Получить актуальные тарифы и тестовые лимиты.

### Этап 1. Реализовать провайдер-независимую основу

1. Добавить `Notification`, не подключая A1.
2. Добавить `NotificationAttempt`.
3. Добавить настройки согласия и отписки клиента.
4. Добавить локальные шаблоны.
5. Реализовать расчёт SMS-сегментов.
6. Реализовать компактную публичную ссылку.
7. Добавить интерфейс `NotificationSender`.
8. Реализовать `ConsoleNotificationSender`.
9. Покрыть создание, дедупликацию и повторы unit-тестами.

### Этап 2. Провести ручной пилот A1

1. Подключить отдельный тестовый корпоративный аккаунт.
2. Зарегистрировать тестовое альфа-имя.
3. Зарегистрировать один сервисный шаблон.
4. Отправить сообщения вручную через web-интерфейс.
5. Проверить отображаемого отправителя.
6. Проверить длину, кириллицу и публичную ссылку.
7. Проверить статусы доставки.
8. Проверить каскад Viber -> SMS, если он входит в пилот.
9. Сверить фактическую тарификацию и число сегментов.

### Этап 3. Реализовать A1-адаптер

Только после получения документации:

1. Описать внутреннюю конфигурацию A1 без копирования портальных логинов.
2. Реализовать шифрование API-секрета.
3. Реализовать проверку подключения.
4. Реализовать отправку одного SMS.
5. Передавать или генерировать идемпотентный ключ, если API это позволяет.
6. Сохранять `providerMessageId`.
7. Сопоставить ошибки A1 с нашими типами ошибок.
8. Не повторять постоянные ошибки шаблона, авторизации или номера.
9. Повторять только временные сетевые/серверные ошибки с backoff.
10. Добавить интеграционные тесты с замоканным HTTP A1.

### Этап 4. Получать результат доставки

1. Реализовать подписанный webhook, если его предоставляет A1; либо polling.
2. Сделать обработку повторных событий идемпотентной.
3. Обновлять конкретный `NotificationAttempt`.
4. Рассчитывать общий статус `Notification`.
5. Для каскада запускать SMS только после подтверждённой неудачи Viber.
6. Не создавать вторую SMS-попытку при повторной обработке события.

### Этап 5. Добавить настройки frontend

1. Показать чек-лист подключения A1.
2. Показать состояния `Не настроено`, `Ожидает`, `Подключено`, `Ошибка`.
3. Принимать только разрешённый API-токен.
4. Маскировать номер аккаунта и секрет.
5. Добавить проверку подключения.
6. Добавить тестовую отправку.
7. Добавить предпросмотр текста, кодировки и сегментов.
8. Добавить дневной лимит сообщений.
9. Не позволять включить автоматику без утверждённого шаблона и тестовой отправки.

### Этап 6. Ограниченный production-пилот

1. Подключить одну реальную сервисную компанию.
2. Начать только с SMS и одного шаблона.
3. Ограничить число получателей и дневной объём.
4. Сверять журнал Service Cycle с кабинетом A1 ежедневно.
5. Проверить доставку, отказы, стоимость и дубли.
6. После стабильного пилота включить автоматический scheduler.
7. Затем оценить Viber и каскад.

4. Выдаётся ли отдельный API-ключ, не совпадающий с паролем кабинета?

## Критерии готовности интеграции

Интеграцию нельзя считать готовой, пока не выполнено всё перечисленное:

- API-секрет хранится зашифрованно;
- пароль личного кабинета A1 не хранится;
- утверждённое альфа-имя связано с компанией;
- шаблон согласован;
- клиент с запретом уведомлений исключается до отправки;
- повторная обработка не создаёт дубль;
- длина и сегменты рассчитаны до отправки;
- `providerMessageId` сохранён;
- статус доставки синхронизируется;
- временные ошибки повторяются ограниченно;
- постоянные ошибки не повторяются автоматически;
- дневной лимит действует;
- публичная ссылка безопасна и ограничена по времени;
- тестовая и production-среда разделены;
- журнал не содержит секретов и полный текст чувствительных данных;
- реальный пилот сверён с отчётом A1.
