# Frontend-review Service Cycle

Проверяй frontend как reviewer: ищи ошибки, регрессии и нарушения согласованной архитектуры. Соблюдай корневой `AGENTS.md` и актуальный backend-контракт.

## Граница задачи

- Если пользователь просит только review, не редактируй файлы, не коммить и не отправляй сообщения автору MR.
- Определи base/head или явно укажи, какой локальный diff проверяется.
- Сначала изучи изменённые файлы. Открывай связанный код только когда он нужен для проверки поведения.
- Не превращай review одного MR в аудит всего приложения.
- Игнорируй субъективные вкусовые замечания, если они не влияют на поддержку, согласованность или пользовательский сценарий.

## Порядок проверки

1. Пойми пользовательский сценарий и контракт API, который затрагивает изменение.
2. Проверь функциональную корректность, потерю данных, безопасность и обработку ошибок.
3. Проверь границы Next.js Server/Client Components.
4. Проверь FSD-размещение и направление импортов.
5. Проверь TanStack Query, транспорт API и типы.
6. Проверь Ant Design, состояния интерфейса и доступность.
7. Запусти релевантные статические проверки и тесты, если это возможно без изменения кода.
8. Сформулируй только доказуемые замечания.

## Формат результата

Начинай с найденных проблем в порядке серьёзности:

- `P0` — потеря данных, критическая уязвимость или полностью неработающий основной сценарий;
- `P1` — значимая функциональная ошибка или нарушение безопасности;
- `P2` — ошибка в частом сценарии, архитектурный дефект с реальным последствием;
- `P3` — небольшая проблема качества или редкий edge case.

Для каждого замечания укажи:

1. короткий заголовок;
2. точный файл и минимальный диапазон строк;
3. сценарий, в котором проявляется проблема;
4. конкретное направление исправления.

Не пиши длинное вступление перед findings. Если блокирующих проблем нет, прямо скажи об этом и отдельно перечисли остаточные риски или непроверенные сценарии.

## Архитектура Next.js и FSD

Проверяй:

- направление зависимостей `app -> views -> widgets -> features -> entities -> shared`;
- отсутствие обратных импортов из нижнего слоя в верхний;
- тонкий `page.tsx`, напрямую импортирующий конкретный view;
- отсутствие общего barrel-файла всех views;
- минимальную границу `"use client"` около интерактивного компонента;
- отсутствие browser-only API в Server Components;
- отсутствие серверных секретов и приватных environment variables в клиентском bundle;
- осмысленное разделение route groups `(auth)`, `(workspace)` и `(public)` по мере появления маршрутов.

Не требуй переносить компонент в отдельный слой только ради формального соответствия FSD: замечание должно объяснять реальную проблему зависимостей или повторного использования.

## Серверные данные и API

Проверяй:

- `fetch` используется внутри API-функций, а не непосредственно в UI-компонентах;
- серверные данные и мутации управляются TanStack Query;
- query key содержит все значения, меняющие ответ: идентификаторы, page, limit, filters и search;
- условный запрос использует корректный `enabled`;
- после мутации обновляется или инвалидируется правильный cache key;
- отмена, повторные запросы и смена параметров не показывают данные предыдущего клиента как актуальные;
- cookie-аутентификация отправляет `credentials: "include"` там, где это требуется;
- обработка `401` не создаёт бесконечный refresh/retry цикл и повторяет исходный запрос не более одного контролируемого раза;
- frontend не хранит access/refresh token в `localStorage`, если backend использует HttpOnly cookies;
- API errors преобразуются в понятное состояние UI без потери исходного status code там, где он нужен логике.

## Контракты и типы

- NestJS DTO и Swagger/OpenAPI остаются источником контракта.
- Используй типы из `shared/api/generated`; не одобряй ручную копию интерфейса ответа backend.
- Не редактируй сгенерированные типы вручную.
- Сверяй optional и nullable: отсутствие поля и `null` — разные контракты.
- Проверяй соответствие query/path/body параметров реальному endpoint-у.
- После изменения backend DTO ожидай обновление OpenAPI и сгенерированных frontend-типов.

## UI и Ant Design

Проверяй:

- loading, error, empty и success состояния;
- блокировку повторной отправки формы или мутации во время выполнения;
- отображение серверных ошибок формы;
- корректную очистку локального состояния при закрытии Drawer/Modal;
- управляемые значения пагинации и фильтров;
- стабильный `rowKey` и отсутствие индекса массива в качестве идентификатора;
- доступные подписи полей, кнопок и интерактивных элементов;
- отсутствие кликабельного `div`, если подходит семантическая кнопка или ссылка;
- использование Ant Design tokens и общей темы вместо разрозненных магических цветов;
- отсутствие `@ant-design/v5-patch-for-react-19` в проекте с Ant Design 6.

Для списка клиентов отдельно проверяй, что родитель хранит `selectedClientId`, а Drawer загружает актуальную детальную карточку отдельным запросом. Не требуй отдельный URL карточки, пока продуктовый сценарий этого не требует.

## Проверки

- Запускай наиболее узкие доступные команды для `apps/web`, затем при необходимости корневые `format:check`, `lint`, `typecheck`, `test` и `build`.
- Не запускай автоисправление при review без разрешения: оно изменит diff автора.
- Отличай ошибку MR от ранее существующей ошибки проекта.
- Указывай команды, которые не удалось выполнить, и не выдавай непроверенное за подтверждённое.
