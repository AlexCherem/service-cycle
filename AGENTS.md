# Service Cycle: контекст проекта

## Продукт

- Service Cycle — B2B-сервис для простой загрузки клиентской базы и возврата клиентов на плановое обслуживание оборудования.
- Это не копия Bitrix24 и не универсальная CRM. Главная ценность: напоминание о сервисе, фиксация отклика, задача сотруднику и измеримый возврат выручки.
- Первый релиз должен быть небольшим и ориентированным на один VPS.

## Команда и способ работы

- Проект разрабатывают два человека: пользователь пишет backend и ревьюит frontend; второй разработчик — junior frontend-разработчик.
- Пользователь впервые пишет backend, поэтому изменения нужно делать небольшими шагами.
- Перед добавлением нового слоя или важного файла объяснять его назначение и место в общей цепочке.
- Не создавать много заготовок и пустых файлов заранее. Добавлять структуру вместе с первой реальной функцией.
- Основная совместная работа с Codex: разработка backend и ревью frontend.

## Зафиксированный стек

- Monorepo: pnpm workspaces.
- `apps/web`: Next.js 16, App Router, React 19, TypeScript, Ant Design 6, Turbopack.
- `apps/api`: NestJS 11, TypeScript.
- PostgreSQL, Prisma, Docker Compose.
- Swagger/OpenAPI для документации и контракта API.
- Node.js 22+, pnpm 11+.
- Первоначальное развёртывание: один VPS.

## Команды workspace

- Весь проект: `pnpm dev`.
- Только frontend: `pnpm dev:web` или `pnpm --filter web dev`.
- Только backend: `pnpm dev:api` или `pnpm --filter api dev`.
- Новые зависимости ставить в конкретный пакет через `pnpm --filter web add ...` или `pnpm --filter api add ...`.

## Архитектура frontend

- Использовать облегчённый FSD-подход, адаптированный под Next.js App Router.
- Направление зависимостей: `app -> views -> widgets -> features -> entities -> shared`.
- `app` отвечает за маршруты, layouts и глобальные providers.
- `views` заменяет FSD-слой `pages` и отвечает только за композицию целого экрана.
- `widgets` содержит крупные самостоятельные блоки интерфейса.
- `features` содержит действия пользователя, `entities` — бизнес-сущности, `shared` — общий технический код.
- `page.tsx` должен быть тонким и импортировать конкретный view напрямую, например `@/views/clients`, без общего barrel-файла всех views.
- Использовать route groups `(auth)`, `(workspace)` и `(public)` по мере появления соответствующих маршрутов.
- Не ставить `"use client"` на целый view без необходимости; держать клиентскую границу ближе к интерактивному компоненту.

## Frontend: данные и состояние

- Для серверных данных и мутаций использовать TanStack Query. Нативный `fetch` оставлять транспортом внутри функций API, а не вызывать напрямую из UI-компонентов.
- Функции запросов размещать в `api` соответствующей feature/entity, общую конфигурацию API — в `shared/api`.
- Типы ответов генерировать из Swagger/OpenAPI, источником контракта остаются NestJS DTO. Сгенерированные файлы хранить в `shared/api/generated`, коммитить в Git и не редактировать вручную.
- Локальные состояния интерфейса — выбранный файл, шаг импорта, открытая модалка и выбранная строка таблицы — хранить рядом с использующим их компонентом через `useState`.
- Не добавлять Redux или RTK Query без конкретного сценария сложного глобального клиентского состояния. Серверный кеш не считать основанием для Redux: его ведёт TanStack Query.
- Для быстрого просмотра клиента на `/clients` использовать таблицу и Ant Design Drawer без изменения URL на первом этапе.
- Таблица клиентов должна оставаться плоской: одна строка соответствует одному клиенту, а оборудование перечисляется компактно в одной колонке без expandable-строк.
- При клике по строке сохранять только `selectedClientId` в локальном состоянии родительского компонента. Drawer открывать через `open={Boolean(selectedClientId)}` и закрывать сбросом `selectedClientId` в `null`.
- Детальные данные клиента загружать внутри Drawer отдельным `useQuery` с ключом, содержащим авторизованный `companyId` и `clientId`, и с `enabled: Boolean(clientId)`. `companyId` нужен только для изоляции frontend-кеша; HTTP-запрос передаёт `clientId`, а backend получает компанию из access-токена. Не хранить полную выбранную строку как источник детальных данных, чтобы не показывать устаревшую информацию.
- Таблица и Drawer должны быть соседними частями одного клиентского компонента/виджета: таблица выбирает `clientId`, Drawer получает его через props и самостоятельно запрашивает детали.
- Отдельный маршрут `/clients/[clientId]` добавлять позже только при реальной необходимости прямых ссылок, сохранения открытой карточки после перезагрузки или полноценного большого экрана клиента.
- Отдельную страницу оборудования строить как таблицу всего реестра компании с поиском и фильтрами; одна строка соответствует одной единице оборудования.
- По клику на строку оборудования открывать Drawer с техническими данными, сервисными датами и историей. Этот Drawer переиспользовать и при переходе из карточки клиента.
- Историю обслуживания показывать внутри Drawer оборудования, но загружать отдельным пагинированным запросом.
- Первый вариант страницы «Обслуживание» делать таблицей запланированных и выполненных работ с фильтрами и Drawer одной работы; календарь добавлять только при подтверждённой необходимости.

## Ant Design

- `antd` и `@ant-design/icons` уже установлены в `apps/web`.
- Для App Router при первой UI-задаче подключить `@ant-design/nextjs-registry` через один корневой `AntdRegistry`.
- Общие React/Ant providers держать в `app/providers`, а типизированную тему — в `shared/config/antd`.
- Начать с небольшого набора глобальных token-ов из дизайна; component token-ы добавлять только при реальной необходимости.
- Не использовать `@ant-design/v5-patch-for-react-19`: проект работает на Ant Design 6.
- Для первых форм использовать правила `Form` из Ant Design. Yup не установлен; Zod оценить при появлении первой сложной формы или общего контракта.

## Архитектура backend

- Модульный монолит NestJS, без микросервисов.
- Основная цепочка: `Controller -> Service -> Prisma -> PostgreSQL`.
- Разделять код по бизнес-модулям: companies, users, clients, equipment, imports, service-events, notifications, service-requests.
- Не добавлять отдельный Repository-слой на старте без реальной необходимости.
- Данные арендаторов изолировать через `companyId`.

## Контракты API

- Все HTTP endpoint-ы используют глобальный префикс `/api/v1`; Swagger доступен по `/docs`.
- NestJS DTO являются источником Swagger/OpenAPI-контракта.
- Типы frontend генерировать из OpenAPI, не переписывать DTO вручную и не создавать параллельные интерфейсы с теми же полями.
- Общий пакет `packages/contracts` пока не создавать: типизированный frontend опирается на сгенерированную OpenAPI-схему.
- В защищённых tenant-endpoint-ах `companyId` получать из access-токена. Список клиентов и импорт временно сохраняют `companyId` в URL до готовности frontend login/refresh.

## Качество кода

- Общий формат задают корневые `.prettierrc.json` и `.editorconfig`.
- Проверки из корня: `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
- Автоисправление: `pnpm format` и `pnpm lint:fix`.
- `lint` не должен изменять файлы; для изменений существует отдельный `lint:fix`.
- Импорты автоматически сортирует `eslint-plugin-simple-import-sort`; frontend-группы учитывают слои `app`, `views`, `widgets`, `features`, `entities`, `shared`.
- Husky, lint-staged и GitHub Actions ещё не подключены; добавлять их отдельным следующим этапом.

## Backend-инфраструктура

- PostgreSQL 17 запускается через корневой `compose.yaml` и доступен с хоста на порту `5433`.
- Prisma 7 подключён к NestJS через `PrismaModule` и PostgreSQL-драйвер `@prisma/adapter-pg`.
- Prisma Client генерируется в `apps/api/src/generated/prisma` и не хранится в Git.
- Корневой `.env` используется Docker Compose; `apps/api/.env` используется NestJS и Prisma.

## Как определять текущее состояние проекта

- Не считать `AGENTS.md` источником списка уже реализованных функций: такой список быстро устаревает.
- Перед backend-задачей проверять актуальные модели в `apps/api/prisma/schema.prisma`, миграции в `apps/api/prisma/migrations` и подключённые модули в `apps/api/src/app.module.ts`.
- Перед изменением существующего модуля изучать его controller, service, DTO и тесты.
- Текущие продуктовые решения зафиксированы в `docs/product/domain-and-notification-strategy.md`.
- Исследование интеграции A1 зафиксировано в `docs/product/a1-smart-sender-integration.md`.
- Не реализовывать реальный адаптер A1 до получения API-документации, разрешения на серверную интеграцию и тестового доступа.
- Приоритет следующей задачи определять по актуальному запросу пользователя и состоянию кода, а не по устаревшему roadmap в инструкциях.
